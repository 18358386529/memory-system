1. **haven-ombre 的真实调用链**(以 `server.py` 内 breath/回忆 相关端点为例,L6055-6100):关键词检索 `bucket_mgr.search()` 产出 `matches` → 补一轮 `embedding_engine.search_similar(search_query, top_k=...)` → 按 `bucket.get("id") not in matched_ids and sim_score >= vector_min_score` 把语义候选并入同一个 `matches` 列表,标记 `bucket["vector_match"] = True` → 之后才进入排序/展示逻辑。`recall_policy.py`/`entity_edges.py`/`memory_edges.py`/`memory_moments.py` 在这条链路里**不参与向量部分**,它们各自服务于:`recall_policy.py`(准入门槛判定,基于正则抽取的实体/情绪/事实项)、`entity_edges.py`(用正则从文本抽取 `likes/dislikes/prefers/fears/boundary/habit` 等关系存 JSON)、`memory_edges.py`(`RELATION_TYPES` 定义的显式记忆关系,JSONL 存储于 `state_dir/memory_edges.jsonl`)、`memory_moments.py`(按 `SECTION_ALIASES` 把桶正文切分为 moment/fact/context/feeling 等语义段)。这些模块的输入是**已经合并好的桶字典**,不关心桶是靠关键词还是靠向量召回进来的。
2. **ombre-brain 参考实现的调用链**更紧耦合:`BucketManager.__init__` 直接持有 `embedding_engine` 引用,`search()` 内部按 `w_semantic=2.5` 权重把 `_get_semantic_candidates()`(`embedding_engine.search_similar` 的封装)的余弦分数并入加权求和公式,与 `w_bm25=1.5`(BM25Index)、`w_topic=4.0` 等一起参与统一打分,而不是像 haven-ombre 那样"先各自检索、再取并集"。
3. **xinchao-nian 外层**(`main.py`/`database.py`/`dream.py`/`tool_drawer.py` 等根目录文件)本身**没有独立的 embedding 依赖**,其记忆能力完全通过内嵌的 `ombre-brain/` 子目录副本提供;`grep -rn "embedding" --include="*.py"` 在 xinchao-nian 根目录只命中 `main.py`/`tool_drawer.py`/`dream.py`/`config.py`/`database.py`/`daily_digest.py`,均为测试脚本(`scripts/test_kiwi_safety_sync.py`、`scripts/test_mcp_recall.py` 等,不属于生产路径,unknown 是否为误报——已在证据ID中注明需人工二次确认这批文件的实际用途)。
4. **kiwi-mem 确实有一套独立的 embedding 实现,内嵌在 `database.py`(296KB 单文件)内,未使用 `embedding_engine.py` 这类独立文件名,故初次按文件名/类名搜索未命中,后续按函数级 grep 补充核实,结论更正如下(修正本报告更早版本"标注 unknown"的过度保守结论)**:
   - **模型**:`EMBEDDING_MODEL = os.getenv("EMBEDDING_MODEL", "openai/text-embedding-3-small")`(`database.py` L40),可被面板配置项 `default_embedding_model` 覆盖(`_resolve_embedding_endpoint()`,L824-850)。与 haven-ombre/ombre-brain 的 `gemini-embedding-001`/`bge-m3` 均不同,是第三种默认模型。
   - **维度**:代码中未发现任何维度常量或一致性校验(`grep -n "1536\|3072\|1024\|dimension" database.py` 零命中),向量原样存入,无维度校验机制。
   - **归一化**:否——`cosine_similarity()`(L922-928)与其余三个仓库同款手写实现(`dot/‖a‖·‖b‖`),存储前不归一化。
   - **相似度算法**:cosine,且明确采用 **RRF(Reciprocal Rank Fusion,`RRF_K=60` 环境变量可调)** 做向量检索与关键词检索的混合排序(`database.py` 文件头注释 L1-15:"v5.7 升级:RRF 混合检索——向量搜索和关键词搜索并行执行(asyncio.gather)、Reciprocal Rank Fusion 合并两路结果"),另有独立的加权分数 `WEIGHT_SEMANTIC=0.5`/`WEIGHT_IMPORTANCE=0.15`/`WEIGHT_RECENCY=0.1`/`WEIGHT_HEAT=0.25`(合计1.0,L42-45)用于 RRF 之后的再排序,检索架构与 ombre-brain 的"加权求和"、haven-ombre 的"关键词候选+语义候选取并集"均不相同,是第三种设计。
   - **存储位置**:**PostgreSQL**(经 `asyncpg` 连接,`DATABASE_URL` 环境变量),表 `memories.embedding` 列类型为 `TEXT`(JSON 序列化数组,L124-133 `ALTER TABLE memories ADD COLUMN embedding TEXT`)、表 `mem_scenes.embedding` 列类型为 `JSONB`(L419,L436)。**未使用 pgvector 扩展**——`grep -in "create extension\|vector(" database.py` 零命中,列类型是普通 `TEXT`/`JSONB` 而非 `vector(n)`,相似度计算在 Python 应用层完成(`cosine_similarity()`),不是靠 SQL 侧的 `<=>` 向量算子(`grep "<=>" database.py` 零命中)。
   - **缓存机制**:未发现进程内缓存结构(`grep "embedding_cache\|_cache\["` 零命中)。
   - **版本(依赖声明)**:kiwi-mem 的 `requirements.txt` 里**没有 `openai`/`google-generativeai` 等 SDK 包**,embedding 请求走的是自行拼接的 `httpx.AsyncClient().post(url, json={"model": model, "input": text})`(L855-869),`url` 由 `API_BASE_URL`(默认 `https://openrouter.ai/api/v1/chat/completions`)动态推导出 `/embeddings` 后缀而来,即通过 **OpenRouter 风格的通用网关**发起请求,不锁定具体供应商 SDK。
   - **依赖(上下游)**:上游为 `httpx`(REST 调用)、`asyncpg`(存取)、内部 `config.get_config()`/`resolve_provider_for_model()`(供应商路由,与 kiwi-mem 自己的聊天模型路由复用同一套供应商配置)。下游调用点包括 `search_memories`(L2784 一带,普通记忆向量检索)、场景匹配(L5860-5893,"Search active scenes by embedding similarity for Dream scene injection")、文件分片检索(L6439-6458,`chunk_emb` 命名暗示文档/附件分片检索也走同一套 embedding)。
   - **重建影响(结构性)**:换模型会导致 `memories.embedding`/`mem_scenes.embedding` 两列里全部历史向量与新模型输出维度不再可比;由于**没有任何维度/模型一致性校验代码**(不像 ombre-brain 有 `embeddings_meta` 表和 OB-W005 告警,也不像 haven-ombre 有按 `model` 字段过滤的 `_row_matches_current_model`),`cosine_similarity(a, b)` 在 `len(a) != len(b)` 时目前的实现是 `zip(a, b)` 截断到较短向量长度后计算点积再除以两者各自完整范数——**这是一个潜在的正确性风险**:不同维度的新旧向量混在一起检索时,`cosine_similarity` 不会报错也不会显式判 0,而是产出一个数学上无意义但格式合法的相似度分数,可能被误判为真实语义相关。此风险与 haven-ombre/ombre-brain 的"显式过滤/显式判0"设计形成对比,换模型前必须先人工核实这条路径,而不能照搬另外两个仓库"静默跳过"或"记警告"的假设。
   - **证据ID**:kiwi-mem@b01a0c5: `database.py` L1-16(模块头注释),L34-51(`EMBEDDING_MODEL`/权重/`RRF_K`/`API_BASE_URL`),L75-80(`asyncpg.Pool`),L124-133(`memories.embedding` 列迁移),L419,L436(`mem_scenes.embedding` 列),L824-901(`_resolve_embedding_endpoint`/`get_embedding`/`get_embeddings_batch`),L922-928(`cosine_similarity`),L2784,L5860-5893,L6439-6458(调用点);`requirements.txt` 全文(确认无 `openai` 包)。

## 发现的冲突与待人工裁决项

1. **Supabase / pgvector 现状(任务书重点关注项)**:逐字节核对 `sync_to_supabase.py` 与 `supabase_memory_rpc.sql` 后,**未发现** `vector`/`pgvector`/`embedding` 关键词,`memories` 表的字段清单里没有向量列。结论:就本次审计到的 haven-ombre@284c9c7 源码而言,**embedding 向量没有被同步到 Supabase**,约束4("禁止引入 PostgreSQL/pgvector/第二套 embedding")**在当前代码里未被触碰**。但这只是静态代码结论,不代表线上 Supabase 项目的实际表结构(可能有本次快照之外的手工 DDL 变更,或未纳入本次克隆范围的其他分支/脚本),**是否可以据此完全排除风险,请人工用 Supabase 控制台或 `\d memories` 直接核实实际表结构后再下结论**。
2. **任务书假设的 embedding→recall→edge→moment 依赖链在 haven-ombre 源码中不成立**:`recall_policy.py`/`recall_diagnostics.py`/`recall_eval.py`/`entity_edges.py`/`memory_edges.py`/`memory_moments.py` 六个文件均不直接引用 embedding。这与 `embedding_engine.py` 文件头注释("Depended on by: server.py, bucket_manager.py")**也不一致**(`bucket_manager.py` 实测未依赖它)。请人工确认:①这是过时的文件头注释(技术债),②还是审计范围理解有误,③还是另有一份未克隆到的模块间接建立了这条链路。这直接影响"换 BGE-M3 会破坏哪些下游"的范围判断,不宜在文档不一致的情况下直接采信任务书给的清单。
3. **haven-ombre 与 ombre-brain 参考实现的默认 embedding 模型均非 BGE-M3**:两者的云端默认路径都是 Gemini 的 `gemini-embedding-001`(维度自校正,常量兜底 3072 维);`bge-m3`(1024 维)仅在 ombre-brain 的**本地 Ollama 后端分支**里作为默认模型名出现,haven-ombre 完全没有 `bge-m3` 字符串(`grep` 零命中)。若"记忆系统2.0"的 BGE-M3 迁移目标是要把**生产默认路径**从 Gemini 云端 API 切到 BGE-M3,这是一次跨维度(3072→1024,任务书里未指明目标维度,以实测为准)、跨提供商(云端 API→本地/自托管模型)的替换,而不是同维度的模型换血;两个仓库现有的"元数据一致性校验"设计(haven-ombre 无校验会静默清零、ombre-brain 有 `OB-W005` 告警但仍需人工触发重算)都需要人工确认是否满足新的迁移场景,本报告不提出迁移方案,仅指出结构性事实。
4. **xinchao-nian 内嵌 ombre-brain 副本与上游参考实现已出现依赖声明漂移**:`requirements.txt` 里 `mcp` 的版本约束从上游的 `mcp>=1.27,<2` 松绑为 `mcp>=1.0.0`,而各自的 `requirements.lock.txt` 又分别锁定了 `openai==2.52.0`(上游)与 `openai==2.45.0`(内嵌副本)两个不同的次要版本。`src/embedding_engine.py` 本身 `diff` 后有 526 行差异,不是简单的文件级同步。这意味着"以 ombre-brain 参考实现的行为去推断 xinchao-nian 内嵌副本的行为"存在风险,任何涉及 embedding 迁移的改动都需要**分别**在两处验证,不能假设两者行为一致。
5. **BM25 与 embedding 的关系已在源码注释里被自我否定为"名义混合、实为纯关键词"**:ombre-brain 的 `bucket_manager.py` 权重注释明确写出语义分量仅占约 18.5% 总分,且附带了作者本人的人工扫描数据(0.65→0.55 阈值调整的实测表格)。这意味着评估"换模型影响面"时,**默认混合检索路径**的影响可能被高估,而**纯语义直通路阈值 `_VECTOR_RECALL_THRESHOLD=0.55`** 的失效风险可能被低估——这一细节是否已被记忆系统2.0团队注意到,建议人工确认。
6. **haven-ombre 是否移植了 ombre-brain 的 BM25 混合检索,未能在预算内做进一步交叉验证**,已在正文标注为"零命中",建议团队内部二次确认。
7. **kiwi-mem 存在第三/第四套独立的 embedding 实现,且直接使用 PostgreSQL 存储向量(TEXT/JSONB 列,非 pgvector 类型)**——这一点在本报告早期版本中曾因文件名搜索未命中而误判为 unknown,后经函数级 grep 补充核实予以更正。虽然 kiwi-mem 仅是"算法参考"对象、其 PostgreSQL 选型是该仓库自身既有架构、并未被引入 haven-ombre/ombre-brain/xinchao-nian 三个仓库,不构成对约束4("禁止引入 PostgreSQL/pgvector/第二套 embedding"面向 haven-ombre 的直接违反,但如果记忆系统2.0团队计划参考 kiwi-mem 的 RRF 混合检索思路或数据模型,需要清楚意识到:①kiwi-mem 的模型默认值是 `openai/text-embedding-3-small`,既不是 BGE-M3 也不是 Gemini,是第三种基线;②它的向量维度/模型一致性完全没有校验,`cosine_similarity` 对不同长度向量会静默截断计算出一个格式合法但语义无意义的分数,这是一个比另外两个仓库更脆弱的设计,若参考其代码结构需额外补上一致性校验,而不能照单全收。这一发现请提请人工确认是否需要在"BGE-M3 替换"范围说明里明确排除 kiwi-mem(即声明 kiwi-mem 的 embedding/PostgreSQL 架构不在本次迁移影响范围内)。
